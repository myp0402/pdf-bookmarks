# PDF 书签补全工具（Mac 版 Word 专用）

Mac 版 Word 导出 PDF 时**不会**生成 `/Outlines`（侧边栏大纲/书签），Windows 版才有。
这个工具绕过该缺陷：**排版交给 Mac Word 保证 100% 正确，书签由脚本事后补上。**

## 原理

PDF 大纲只是文档目录里的一个对象树，跟页面内容、字体、排版毫无关系：

```
docx ──(Mac Word 导出)──> PDF 页面内容 + 嵌入字体     ← 排版这件事 Word 做得很好
docx ──(本脚本)────────> /Outlines 书签树            ← Word 没做的那件事
```

脚本做的事只有三件：

1. 从 `.docx` 按文档顺序读出所有标题（`标题 1/2/3` 样式、或 `w:outlineLvl`）及其层级；
2. 在 PDF 里按**阅读顺序单调递增**地定位每个标题所在的页（用文字 + 字号 + 粗体打分）；
3. 用 PyMuPDF 的 `set_toc()` 写入大纲树，页面内容一个字节都不动。

因为不参与排版，**字体、分页、图表、公式全部保持 Mac Word 导出的原样**，这也正是它比"虚拟机重排一遍"更安全的地方。

## 安装

```bash
python3 -m venv .venv
.venv/bin/pip install pymupdf python-docx
```

> 若 `import pymupdf` 报 `code signature ... different Team IDs`，说明当前 Python 带强化运行时签名，
> 换一个 python.org 或 conda 的解释器建 venv 即可（本项目实测 conda 3.12 正常）。

## 用法

```bash
# 1) 先预览：只打印「标题 → 页码」对应关系，不写文件
.venv/bin/python bookmark_pdf.py 报告.docx 报告.pdf

# 2) 确认无误后生成
.venv/bin/python bookmark_pdf.py 报告.docx 报告.pdf -o 报告-带书签.pdf

# 3) 导出匹配明细，便于逐条核对
.venv/bin/python bookmark_pdf.py 报告.docx 报告.pdf -o out.pdf --report 明细.tsv
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--max-level N` | 只收录到第 N 级标题（默认 9） |
| `--toc-pages 2,3` | 手工指定要跳过的目录页，覆盖自动识别 |
| `--margin-ignore 0.07` | 忽略上下各 7% 的页眉页脚区域 |
| `--report 文件` | 输出 `页码/级别/得分/标题/匹配行` 明细 |

## 已处理的坑

| 坑 | 处理方式 |
|---|---|
| 文档自带目录页：标题文字在正文前先出现一次 | 双信号识别：①点线/制表符+页码结尾的行 ≥2 条；②该页命中 ≥3 个标题**且整页 ≥55% 都是标题行**。只有 ① 会误伤“一页刚好有 3 个小标题”的正文页，故 ② 加了占比门槛 |
| 页眉里写着章名，每页都重复 | 按上下边距带裁掉页眉页脚，不参与匹配 |
| 标题用自动编号（`1.1`、`第三章`），docx 里没有 | 归一化后做"后缀匹配"，行首编号不影响定位 |
| 长标题在 PDF 里折成两行 | 把相邻同字号行拼接后再比对 |
| 书名标题只出现在封面，正文里没有 | 第一遍跳过目录/封面页；找不到时第二遍回落，按目录页登记并标注"待核对" |

另外用**单调游标**保证页码顺序不倒流，用**字号/粗体打分**区分"正文里顺带提到标题词"和真正的标题。

## 实测（`fixture.docx` + `fixture.pdf`，6 页 7 个标题）

```
   页   级  标题                                匹配到的 PDF 行
   2  H1   引言                                第一章 引言
   2  H2   背景                                1.1 背景
   3  H2   目标与范围                          1.2 目标与范围
   4  H1   方法与实现                          第二章 方法与实现
   4  H2   数据来源                            2.1 数据来源
   5  H2   一个特别长的标题，用来测试 PDF …    2.2 一个特别长的标题，用来测试 PDF 里的折行情况
   6  H1   结论                                第三章 结论
```

回读输出文件的 `get_toc()`：

```
H1 引言 → p2
  H2 背景 → p2
  H2 目标与范围 → p3
H1 方法与实现 → p4
  H2 数据来源 → p4
  H2 一个特别长的标题，用来测试 PDF 里的折行情况 → p5
H1 结论 → p6
```

`make_fixture.py` 可随时重建这两份样例（其中埋了目录页、页眉、自动编号、正文误提、标题折行、同名候选等 6 个陷阱）。

另在一份真实的 6 页中文教材节选上验证（正文页恰好包含 3 个标题，正是上面信号 ② 容易误判的情形）：
8 个标题全部命中，其中封面书名按“目录页回落”登记为第 1 页，并给出待核对提示。

## 局限（请务必先预览）

- 只认 **Word 内置标题样式或显式大纲级别**。手打加粗当标题的，脚本看不见——先在 Word 里套样式（也是生成书签的唯一正确姿势）。
- 定位基于文本，**同名标题**、标题只出现在文本框里、OCR 型扫描 PDF 会不可靠；预览表里得分 < 60 的条目会单独告警。
- 页眉页脚如果压到正文区域（`--margin-ignore` 太小），可能混入匹配。
- 输出是重写文件：页面内容、链接、注释保留；**数字签名会失效**。
- 不生成"跳转到章节末"之外的任何结构，纯大纲。

## 与虚拟机方案对比

| | 本脚本 | Windows 虚拟机 + PDFMaker |
|---|---|---|
| 排版正确性 | 100%（Mac Word 原样输出） | 取决于字体是否齐全，可能静默替换 |
| 书签 | 事后计算，需预览核对 | 原生生成，层级最准 |
| 字体/授权成本 | 无 | 需处理跨平台字体差异 |
| 处理速度 | 秒级 | 需开虚拟机 |
| 大文档稳定性 | 标题几百个也很快 | 同左 |

日常用本脚本；对书签层级有极高要求（比如要按"标题 + 书签"混合出大纲、或要严谨的结构化 PDF）时再上 Windows。
